# Multi-Agent Platform V2.1：运行时加固与执行证据计划

> 状态：已完成
> 阶段编号：Phase 7
> 制定日期：2026-08-17
> 验收记录：[Phase 7 验收记录](phase7-acceptance.md)
> 知识来源：对 DeepSeek Harness 的架构、生命周期、子进程、沙箱、工具流水线、会话、子代理、凭据、运行时不变量、测试策略和事故复盘文档进行对照分析后形成。

## 1. 背景

Multi-Agent Platform V2 已完成 Phase 1–6，建立了以下核心能力：

- Temporal 持久化工作流运行时；
- PostgreSQL 控制面、执行租约、Inbox、Outbox 和查询投影；
- DAG、状态机、审批、事件等待、Timer 和 Schedule；
- Codex `AgentRuntime`、显式模型与推理等级、会话恢复和流式事件；
- Windows 本机工作区 allowlist、独立 Git worktree 和安全清理；
- Webhook、Git Connector、CloudEvents 和局域网部署边界；
- Fake、Temporal、PostgreSQL、Docker Compose 和真实 Codex 分层验收。

当前架构已解决“工作流如何可靠推进”的问题。下一阶段不替换工作流底座，而是进一步解决：

1. 本机 Agent 和辅助进程是否真正受控；
2. 声明的沙箱和网络策略是否能够被证明；
3. Provider 执行过程是否留下足够的恢复、审计和 UI 回放证据；
4. 平台自有工具是否具有统一、不可绕过的策略流水线；
5. 真实交付入口、异常退出和资源回收是否具备长期回归保护；
6. 未来动态子代理委派是否拥有稳定的身份、谱系和资源约束。

## 2. 不变的架构决策

Phase 7 必须遵守以下边界，不得因吸收其他项目经验而改变：

1. **Temporal 是唯一的持久化工作流执行事实源。**
   PostgreSQL 保存控制面事实、执行租约、外部事件和查询投影，但不得反向推进 Workflow。
2. **Provider 拥有自己的 Agent loop。**
   Codex、Claude、Copilot 等 Provider 内部的模型循环和工具循环不由平台重新实现。
3. **Agent Runtime 是 Provider 适配边界。**
   平台负责请求契约、模型选择、策略、工作区、幂等、取消、恢复和结果验证。
4. **执行证据不等于执行状态。**
   新增的事件日志、transcript 和 artifact 只能用于审计、恢复证据和 UI 投影，不能成为第二套工作流状态机。
5. **平台只调用同一台 Windows 主机上的本地 Agent。**
   本阶段不增加远程 Agent、跨主机 Worker、登录系统或云端密钥托管。
6. **默认不授予提交、合并或推送能力。**
   这些操作仍必须作为独立的高权限 Activity 显式设计。

## 3. 非目标

Phase 7 不实施以下内容：

- 引入 Cordis、Fiber、HMR 或 DeepSeek Harness 的插件运行时；
- 使用 Harness Workflow、LangGraph checkpoint 或其他运行时推进同一个 Temporal Workflow；
- 在平台中重新实现 Codex 等 Provider 的内部工具循环；
- 将每个 token 写入 Temporal History；
- 将 Provider API Key 写入模板、API 请求、Temporal input、PostgreSQL 或日志；
- 为兼容旧接口保留多套并行实现；
- 开放远程 Agent、公共互联网访问或跨主机执行。

## 5. 7A：受管子进程

### 5.1 目标接口

新增独立的进程能力边界，暂定包名：

```text
packages/process_runtime/
```

接口需要覆盖：

- 可执行文件解析；
- 完全显式的 spawn spec；
- argv 数组执行，禁止隐式 shell 解释；
- 工作目录和环境变量显式传入；
- stdin/stdout/stderr 的明确处置方式；
- 有界内存输出和可选 spill；
- PID 与进程创建时间；
- 进程树级取消和终止；
- 等待整棵进程树完全停稳；
- 服务关闭时回收所有登记进程。

### 5.2 环境变量规则

默认父进程环境必须清除名称包含以下片段的变量：

- `KEY`
- `SECRET`
- `TOKEN`
- `PASSWORD`

调用方只能通过显式 allowlist 或显式 `env` 项传递确有必要的变量。日志、错误、heartbeat 和 Artifact 元数据不得记录环境变量值。

### 5.3 输出规则

每个输出流独立配置：

- 最大内存保留字节数；
- 最大完整输出字节数；
- 是否允许 spill；
- spill 文件相对引用；
- 是否发生截断；
- 是否能够从 spill 恢复完整输出。

spill 文件必须位于 Artifact Root 管理的私有目录中，使用随机文件名、原子创建和严格权限。

### 5.4 终止语义

以下事实必须独立上报，不得压缩成单一 success/failure：

- `exit_code`
- `signal`
- `timed_out`
- `cancel_requested`
- `cancel_confirmed`
- `tree_quiescent`
- `output_truncated`

在 Windows 上，优先评估 Job Object `KILL_ON_JOB_CLOSE`；如果只能使用 PID 枚举，则必须结合进程创建时间防止 PID 重用。

### 5.5 Codex SDK 边界

当前 Codex 子进程由 SDK 管理。Phase 7 必须先确认 SDK 是否支持：

- 注入进程工厂；
- 暴露 CLI PID 或进程句柄；
- 等待进程树退出；
- 将进程加入平台 Job Object。

如果 SDK 不提供这些能力：

1. Runtime 必须报告 `process_supervision=sdk_managed` 或 `unknown`；
2. 不得把它描述为平台完全监督；
3. 需要完整进程监督的策略必须拒绝执行；
4. 再单独评审 CLI transport wrapper 或受控宿主方案。

### 5.6 验收

- 子进程产生多级子孙进程后，取消能够使整棵树退出；
- terminate 返回前必须确认完全停稳；
- 输出超限不会导致 Worker 内存无限增长；
- 环境清理测试证明敏感变量不会到达测试子进程；
- Worker 正常退出和异常退出后无登记进程残留；
- PID 重用场景不会误杀无关进程；
- 所有错误路径均在有界时间内结束。

## 6. 7B：沙箱证明

### 6.1 目标

将“请求了什么策略”和“宿主实际上强制了什么”分开建模。

建议新增：

```text
SandboxAttestation
- filesystem: full | partial | unavailable
- network: full | partial | unavailable
- process_tree: supervised | sdk_managed | unknown
- backend
- effective_policy
- limitations[]
```

### 6.2 规则

- 每次 Agent 执行都携带完整、不可变的策略；
- Runtime 不使用 Provider 隐式默认值；
- `read_only` 必须有可验证的文件系统写入限制；
- `network_policy=deny` 必须有平台或 Provider 可证明的强制机制；
- 只达到 `partial` 时必须向上暴露；
- 策略要求 `full` 而宿主无法提供时直接拒绝；
- 沙箱 runner 故障、正常权限拒绝和 Agent 子进程失败必须使用不同错误类型。

Git worktree 仅隔离目标仓库，不等价于完整文件系统沙箱。

### 6.3 验收

- read-only Agent 无法修改工作区和工作区外测试文件；
- workspace-write Agent 只能修改分配的 worktree 和明确允许的临时目录；
- 网络拒绝策略有真实探针；
- 沙箱后端缺失或异常时不会静默无隔离运行；
- UI 和审计记录展示实际 enforcement，而不是只展示请求策略。

## 7. 7C：执行证据与 Artifact Store

### 7.1 执行证据

新增仅追加的 Agent 执行证据流。建议事件至少包括：

```text
execution_registered
lease_acquired
workspace_prepared
session_prepare_intended
session_prepared
turn_start_intended
turn_started
provider_event_observed
output_validated
provider_terminal_observed
cancellation_requested
cancellation_confirmed
reconciliation_required
artifact_committed
cleanup_started
cleanup_completed
cleanup_preserved
cleanup_failed
```

每条事件至少包含：

- `event_id`
- `execution_id`
- `attempt_id`
- `sequence`
- `event_type`
- `occurred_at`
- `provider`
- 可选的 `provider_session_id`
- 可选的 `provider_turn_id`
- 可序列化且经过脱敏的 payload

### 7.2 事实源边界

- Temporal 继续拥有 Workflow 和 Node 状态；
- `agent_executions` 继续拥有外部执行租约与对账状态；
- Agent 执行事件只保存已观察事实；
- 查询投影可以从证据事件更新，但不能触发 Workflow 推进；
- 实时 token 仍进入有界 Stream Hub；
- 只有重要里程碑、最终消息和恢复证据需要持久化。

### 7.3 Artifact Store

将当前 Artifact Root 健康探针扩展为正式存储 seam：

- 服务端生成 artifact ID 和相对路径；
- 临时文件写入、flush、fsync、原子 rename；
- SHA-256、大小、媒体类型和创建时间；
- 原始 Provider 事件和 UI 脱敏版本分离；
- 补丁、最终输出、完整 spill 和诊断包可作为 artifact；
- 不在数据库中保存任意绝对路径；
- Artifact 引用不能作为授权凭据；
- 读取时重新校验 workspace/execution 归属。

### 7.4 崩溃恢复

- Provider terminal 后、Artifact 提交前崩溃：通过 Provider session/turn 对账；
- Artifact 文件写入后、数据库引用提交前崩溃：扫描仅限受管临时文件并安全回收；
- 数据库引用提交后、Activity completion 前崩溃：重试直接返回已提交结果；
- 不确定写任务保留 worktree 和诊断证据，不自动清理。

### 7.5 验收

- 事件 sequence 连续且重复写入幂等；
- 所有 payload 均可 JSON 序列化；
- 原始事件经过脱敏后才进入 UI；
- Artifact 内容、大小和哈希一致；
- 崩溃注入后不会产生两个权威最终输出；
- BFF 重启后可恢复持久里程碑和最终输出；
- Temporal History 不包含逐 token 事件和大块原始输出。

## 8. 7D：真实入口与崩溃验收

### 8.1 测试分层

继续保持三层测试：

1. Fake/单元测试；
2. 无真实推理的本机依赖与安装产物测试；
3. 显式启用的真实 Provider 测试。

### 8.2 必须新增的入口测试

- 构建并安装 wheel；
- 通过安装后的 console script 启动，而不是直接 import 内部函数；
- 覆盖 API、Orchestration Worker、Agent Worker、Dispatcher、Catalog Refresher 和 Preflight；
- 缺失配置时以非零退出码失败；
- 启动失败输出可诊断信息；
- 停止脚本只清理由本次启动创建的进程。

### 8.3 外部世界断言

不得仅检查 Agent 输出中是否出现“成功”。验收必须重新读取：

- 文件内容；
- Git status、diff 和 HEAD；
- PostgreSQL 行；
- Temporal Workflow 状态；
- Artifact 文件与哈希；
- 监听端口；
- 进程树；
- Git worktree 注册。

### 8.4 崩溃注入矩阵

至少覆盖：

- lease 前；
- worktree 创建前后；
- start intent 前后；
- Provider session 创建前后；
- session ID 持久化前后；
- turn 启动前后；
- stream 中；
- Provider terminal 前后；
- Artifact 提交前后；
- execution finalize 前后；
- cleanup 前后。

对每个窗口分别验证 read-only 和 workspace-write 行为。

### 8.5 回归守卫

关键回归测试必须通过以下过程证明有效：

1. 临时重新引入目标缺陷；
2. 验证测试确实失败；
3. 恢复修复；
4. 验证测试重新通过。

## 9. 7E：平台工具执行流水线

本工作包只适用于平台拥有的工具和 Activity，不进入 Provider 内部 Agent loop。

统一流程：

```text
request snapshot
  -> pre hooks
  -> approval resolution
  -> monotonic policy guards
  -> execute
  -> post hooks
  -> output contract validation
  -> immutable result snapshot
  -> audit notification
```

规则：

- Guard 只能拒绝或 abstain，不能放宽先前的拒绝；
- 任一 Guard 拒绝后，工具主体不得运行；
- Approval 缺失、超时、取消或无法回答时默认拒绝；
- 工具名称、调用 ID、参数、策略和执行身份在执行前冻结；
- post hook 可以增加诊断信息，但不能把失败改成未经授权的成功；
- 最终结果必须可 JSON 序列化并满足 output schema；
- 超时、取消、权限拒绝、沙箱故障和工具失败使用不同错误类型；
- 审计和 UI 必须使用同一调用身份。

首批适用对象建议：

- Git 提交与合并；
- Artifact 读取和导出；
- Connector 主动查询；
- 受控本机脚本 Activity。

## 10. 7F：运行时不变量

不引入 Cordis registry，使用适合 Python 服务的轻量注册和检查机制。

首批不变量：

- 一个 execution 同时只能有一个有效 lease epoch；
- terminal execution 不得回到非终态；
- `external_started_at` 后不得自动启动第二个 workspace-write turn；
- 同一个 Provider session 同时只能由一个 execution claim；
- execution event sequence 严格单调；
- stream 只能产生一个 terminal event；
- preserved worktree 不得自动进入 cleanup；
- cleaned worktree 不得恢复为 preserved 或 cleanup_failed；
- PostgreSQL 查询投影不得反向推进 Workflow；
- approval 的同一 activation 只能接受一个决定；
- Event Inbox 同一 source/event ID 只产生一次命令。

运行时不变量默认在开发、测试和验收环境启用；生产环境是否启用高成本检查由配置决定。

## 11. 7G：人工交互契约

建立 Provider 无关的 UI 问题/回答模型：

- 稳定问题 ID；
- 标题、说明和选项；
- 单选、多选和自由文本；
- 可选的展示 intent；
- 问题批次；
- 明确的取消和超时；
- 稳定错误码。

与 Temporal 的映射：

- Workflow 中的长期等待继续使用 Approval/Update/Signal；
- UI provider 只负责展示和收集回答；
- 回答必须通过 Control API 转换为确定性的 Temporal command；
- UI 断开不得丢失已被 Temporal 接受的决定；
- 进程内 `Promise/Future` 不得成为耐久审批事实源。

## 12. 7H：平台凭据引用

适用范围：

- Webhook HMAC；
- Git Connector 的可选本机凭据；
- 未来的局域网内部系统连接器。

规则：

- 配置保存 credential reference，不保存明文值；
- 每次操作重新解析，不跨操作缓存；
- 空值视为未配置；
- UI 只能读取 `configured/source/writable`，不能读取值；
- Secret 更新后下一次操作生效，不要求服务重启；
- 日志、异常、事件和 Artifact 不得包含值。

Provider API Key 仍由 Codex/OpenCodex/其他本机 Agent 自身配置管理，不迁移到平台 Credential Store。

## 13. 7I：动态子代理契约

本阶段只设计和实现最小契约，不立即开放模型自由创建无限子代理。

建议身份字段：

- `child_execution_id`
- `parent_execution_id`
- `root_workflow_instance_id`
- `lineage`
- `depth`
- `provider`
- `model`
- `effort`
- `workspace_id`
- `access_mode`
- `capability_requirements`
- `resource_budget`
- `output_schema`

约束：

- Provider capability 在启动前检查；
- 不支持的能力明确拒绝，禁止静默忽略；
- 绝对最大深度由平台策略限制；
- child 不继承 parent 的隐式权限；
- session/source 身份只用于归因，不自动授予操作权限；
- 同一可继续 Provider session 只能串行执行；
- 取消采用 child-first 资源释放；
- 动态 child 由 Temporal Child Workflow 或现有节点执行模型承载；
- 不引入独立 Activation 状态机推进任务。

资源预算至少预留：

- 最大 child 数；
- 最大深度；
- 最大并发；
- 最大总运行时间；
- 最大 token/成本；
- 最大 Artifact 大小；
- 最大 workspace-write child 数。

## 14. 7J：事件目录

从代码和 schema 自动生成事件目录，至少包含：

- 事件名称与版本；
- 生产方；
- 消费方；
- 传输方式；
- 权威事实源；
- 去重键；
- 顺序保证；
- 是否进入 Temporal History；
- 是否持久化；
- payload schema；
- 脱敏要求。

目录应覆盖：

- Workflow command 和 projection event；
- Agent execution evidence；
- Event Inbox/Outbox；
- CloudEvents；
- Approval；
- Artifact；
- Stream Hub 持久里程碑。

生成检查必须进入 CI，防止新增事件只有字符串而没有所有权和 schema。

7. `Phase 7D - Worker 崩溃注入与残留资源检查`
8. `Phase 7E/7F - 工具流水线与运行时不变量`
9. `Phase 7G/7H - 人工交互和平台凭据引用`
10. `Phase 7I/7J - 动态子代理契约与事件目录`

每个切片只提交本工作包相关变更，禁止 push。

## 17. Phase 7 完成标准

满足以下条件后，Phase 7 才可标记完成：

1. 平台拥有的子进程可以被整树终止并确认完全停稳；
2. 敏感父进程环境不会默认传入受管子进程；
3. 沙箱策略同时展示请求值和实际 enforcement；
4. 无法满足受限策略时 fail closed；
5. Agent 关键生命周期有仅追加、可恢复、经过脱敏的执行证据；
6. Artifact Store 使用原子写入、哈希和服务端生成的相对引用；
7. Temporal 仍是唯一 Workflow 和 Node 执行事实源；
8. 已安装 console entry points 通过真实启动与错误退出验收；
9. Worker 崩溃窗口测试证明不会重复启动不确定的写任务；
10. 取消、超时和失败后无遗留 CLI、进程树、端口或可自动清理的 worktree；
11. 平台自有工具无法绕过单调 Guard 和 Approval；
12. 关键跨模块关系具有运行时不变量与永久回归测试；
13. Provider Key 不进入平台模板、API、数据库、Temporal History、日志或 Artifact；
14. 动态子代理契约具有身份、谱系、深度、能力和资源预算；
15. 全量单元、类型、格式、Temporal replay、PostgreSQL 集成、Docker 拓扑和真实 Codex 验收通过。
